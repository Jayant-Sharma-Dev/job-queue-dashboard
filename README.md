# Job Queue Dashboard

A full-stack job queue management dashboard built with React and NestJS.

The application allows users to create, view, filter, update, and delete jobs while enforcing valid job state transitions on the backend.

## 🚀 Local Setup

### 1. Clone the repository

```bash
git clone https://github.com/Jayant-Sharma-Dev/job-queue-dashboard.git
cd job-queue-dashboard
```

### 2. Backend

```bash
cd backend
npm install
```

Create `backend/.env`:

```env
DATABASE_URL="your-postgresql-connection-string"
```

Run migrations:

```bash
npx prisma migrate dev
```

Start the backend:

```bash
npm run start:dev
```

Backend runs at: `http://localhost:3000`

### 3. Frontend

Open another terminal:

```bash
cd frontend
npm install
```

Create `frontend/.env`:

```env
VITE_API_URL=http://localhost:3000
```

Start the frontend:

```bash
npm run dev
```

Frontend runs at: `http://localhost:5173`

## 📊 Job State Machine

Jobs follow these allowed transitions:

```
PENDING → RUNNING → COMPLETED
    │
    └────────────→ FAILED

RUNNING → FAILED
```

`COMPLETED` and `FAILED` are terminal states.

The backend validates every transition, so invalid transitions cannot be performed by directly calling the API.

## 🔒 Concurrency Handling

A potential race condition occurs when two browser tabs try to move the same job from `PENDING` → `RUNNING` at the same time.

To handle this, the backend performs an atomic database update using the expected current status:

```sql
UPDATE job
SET status = RUNNING
WHERE id = ? AND status = PENDING
```

Only one request can successfully update the job. If another request reaches the database after the status has changed, zero rows are updated and the API returns an error.

This makes the database the source of truth instead of relying on frontend state.

## ⏱️ Production Bonus — Job Duration Tracking

As a production-ready improvement, the application tracks job execution timestamps:

- `createdAt` — when the job was created
- `startedAt` — when the job enters `RUNNING`
- `completedAt` — when the job enters `COMPLETED` or `FAILED`

The dashboard uses these timestamps to display the job's execution duration.

This provides basic observability and makes it possible to identify slow-running jobs.

## 🧠 Key Engineering Decisions

**Backend validation**
State transitions are validated on the backend rather than relying only on frontend buttons. This ensures the rules remain enforced even when the API is called directly.

**Atomic status updates**
Conditional database updates are used to prevent concurrent requests from overwriting each other's state.

**Simple frontend state**
React state is sufficient for this application's scope. After mutations, jobs are refetched to keep the UI synchronized with the backend.

**Server-controlled timestamps**
Job timestamps are generated by the backend during actual state transitions rather than being supplied by the client.
